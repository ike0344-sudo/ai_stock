# 지점 라벨링 1단계 — N/M 분포 실측 결과 (2026-08-30)

## 사전 점검 — point_labeling.py 자체검증 버그 2건 발견·수정
strategy-agent가 "pytest 못 돌려봤다"고 밝힌 대로, `demo()`가 애초에 안 돌아갔다
(`pd.to_datetime(["..."])` 1개 원소 DatetimeIndex + 5개 원소 timedelta 배열 덧셈
— 길이 불일치 에러). 2곳(라인132, 153) `pd.Timestamp(...)`로 수정, 이제 3개
자체검증(순방향윈도우 손계산 일치/라벨판정/미래변경-과거피처불변) 전부 통과
확인. **로직 자체(`_forward_rolling_extreme`/`label_shoot_crash_points`)는
검증 통과 — 실행 오류였지 논리 오류가 아니었다.**

## SQL 이식 검증
`_forward_rolling_extreme`을 DuckDB `RANGE BETWEEN CURRENT ROW AND INTERVAL
(N초-1마이크로초) FOLLOWING`으로 이식 — 반개구간 [t,t+N) 정확히 재현(하한 경계
1마이크로초 트릭). 실제 데이터(010170, 2026-08-13, 61,721틱) 대조: **502/61721
(0.8%) 불일치** — 원인은 동시각(같은 초) 틱의 SQL RANGE 피어그룹 처리(캔들내부
경로 문제와 같은 종류, 이번 세션에 여러 번 나온 한계). 분포 추정(퍼센타일) 목적
상 0.8% 수준 영향은 무시 가능하다고 판단해 그대로 진행했다 — 최종 라벨링(2단계)
때는 이 오차가 라벨 경계에 걸리는 소수 지점에만 영향줄 수 있어 재확인 필요.

## 관찰(판단 없이 숫자만 — 최종 N/M은 같이 정하자고 하셨으니 내가 먼저 고르지 않음)
- **fwd_down이 p90 이상에서 거의 항상 0.0** — 상위 10% 틱은 그 시점 이후 N초
  안에 가격이 시작가 밑으로 전혀 안 내려간다(정의상 fwd_min은 시작가 자신도
  포함해 계산되므로, 0.0은 "그 구간 최저가 = 시작가"라는 뜻). N이 커질수록도
  이 비율(0.0 지점)이 유지된다 — 이 데이터가 momentum 편향(117종목이 애초에
  거래대금 상위/급등 이력 있는 종목들의 합집합)이 섞여 있을 가능성 있음.
- 원하신 대로 "N초 안에 그 정도 오르는 게 드문 사건" 기준으로 보면, 예를 들어
  N=60초에서 M=2.84%(p99)나 M=1.32%(p95) 등이 "상위 1~5%" 후보가 된다 — 어느
  퍼센타일/어느 N을 쓸지는 요청대로 여기서 판단 안 하고 같이 정하겠다.
