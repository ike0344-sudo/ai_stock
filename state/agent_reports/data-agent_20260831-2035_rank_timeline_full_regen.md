# 41일 rank_timeline 15:30 확장 — 착수 직후 중단, 발견 보고

**결론 먼저: 41일 배치를 실행하지 않았다.** 1일치 시간 측정 + 겹침구간 대조를 지시대로
먼저 해봤는데, 그 첫 스텝에서 "불일치가 나오면 멈추고 보고해라" 조건에 바로 걸렸다.
아래는 그 불일치의 원인을 추적한 결과다 — 예상보다 크다.

## 1일치 시간 측정 (지시대로 먼저 잼)

`rank_timeline_20260701.json`을 백업(`.bak60`)해두고
`python -X utf8 -m rank_timeline --date=20260701 --to=15:30` 실행 — **26.0초/일**,
390프레임(09:01~15:30, 예상과 정확히 일치) 생성 확인. 41일 추정 **약 17.8분**
(26s × 41). 부담스러운 시간은 아니라 바로 이어서 겹침구간 대조로 넘어갔다.

## 겹침구간(09:01~10:00) 대조에서 발견한 것

방금 만든 15:30본의 앞 60분을 백업해둔 원본 60분 아카이브와 대조하기 전에, 먼저
"지금 코드로 다시 만들면 기존 60분 아카이브와 완전히 같은가"부터 확인하려고 같은
날짜를 `--to` 없이(기본 10:00) 한 번 더 돌려봤다. **여기서 이미 어긋났다** —
15:30 확장을 시도하기도 전에, **60분짜리를 그대로 다시 만들어도 원본과 안 맞는다.**

- 09:02 `전력` 테마 score: 원본 52.7 vs 방금 재생성 53.3
- 60개 프레임 전체 대조: **score 불일치 322건**(테마×분 조합 기준), 최대 절대
  오차 10.0점(100점 만점), **1위 테마가 뒤바뀐 프레임 3/60개**(2계단도 아니고
  1위 자체가 다름 — 신호 수준의 차이)
- 두 실행 모두 **같은 코드 경로**(KRX 전용 `data/stocks/minute`, `MINUTE_STORE=al`
  미설정)로 돌렸다 — 데이터 소스가 바뀐 게 아니라 같은 코드·같은 분봉인데도
  결과가 다르다는 뜻

### 원인 1 — 기준선/테마 참조 파일이 아카이브 생성 이후 이미 갱신됨
`data/reference/{themes.csv, profile_theme.csv, profile_stock.csv,
profile_market.csv, theme_activity.csv}` 5개 전부 **2026-08-31 10:49**(오늘
장중)에 갱신돼 있다. 원본 41일 아카이브는 **2026-08-29 20:11~20:22**에 일괄
생성됐다(`arch_all.out` 로그와 파일 mtime 확인, 감사 리포트 2015에서도 이미
확인한 사실). 즉 오늘 10:49 이후로 rank_timeline을 다시 돌리면 **08-29 시점엔
없던 참조 데이터**로 계산된다 — 이게 위 322건 불일치의 직접 원인이다. 감사
리포트(2015)에서 "이 기준선은 테마마다 고정된 상수라 날짜간 상대비교엔 영향이
적다"고 썼는데, 그건 "한 배치 안에서는" 맞는 말이고 **"오늘 다시 돌리면 그 상수
자체가 이미 바뀌어 있다"는 걸 놓쳤다** — 정정한다.

### 원인 2 — kospi-theme-engine 워킹트리에 미커밋 상태로 KRX→AL 마이그레이션이 진행 중
`git status`로 확인: `rank_archive.py`, `rank_timeline.py`, `replay.py`,
`universe.py`, `scripts/prepare.py`, `scripts/fetch_minute.py`, `app/main.py`,
`config/theme_group.yaml`, `config/theme_manual.json`, `watch_surge.py`,
`rebuild_after_close.ps1` 등 **12개 파일이 커밋 안 된 상태로 수정돼 있다**
(diff 확인 완료). 핵심 변경: `MINUTE_DIR`을 `data/stocks/minute`(KRX 전용)에서
`data/cache/minute_al`(통합 KRX+NXT)로 바꾸는 마이그레이션 — 주석에 실측 근거까지
적혀 있다("2026-08-28 삼성전자 09~10시: KRX 10,986억 vs 통합 15,642억"). `MINUTE_STORE=al`
환경변수로 켜고 끄게 만들어둔 과도기 상태다. **다른 곳(체결틱 데이터·백테스트 팀)에서
진행 중인 것과 같은 KRX→AL 전환이 이 레포에도 같은 날 들어와 있다** — 우연이
아니라 같은 판단 축이 여기까지 온 것으로 보인다.

이게 위 322건 불일치의 원인은 아니다(내 재실행은 `MINUTE_STORE=al`을 안 켰으니
코드 분기상 여전히 KRX 전용 경로였다) — 하지만 **기존 60분 아카이브 자체가 이미
내부적으로 균일하지 않다.** `results/`를 뒤져보니 `rank_timeline_20260702.json`~
`rank_timeline_20260708.json`(5일치)이 **오늘 19:18~19:20**에 이미 다시 생성돼
있었다(내가 손대기 전, 이 작업 시작 20분쯤 전). 이 미커밋 코드로 부분 테스트를
한 흔적으로 보인다 — 즉 "기존 60분 아카이브"라는 게 이미 08-29 원본과 08-31
재생성본이 섞인 상태다. 대조 기준으로 삼으려던 "기존 60분 아카이브" 자체가
이미 오염됐다.

## 판단: 지금은 못 만든다, 41일 배치 중단

지시에서 금지한 것과 정면으로 부딪힌다 — "고치지 마라, 동일 조건으로만 만들어라"인데
**동일 조건 자체가 지금 존재하지 않는다.** 참조 데이터는 이미 갱신됐고, 파이프라인
코드는 커밋 안 된 채로 절반쯤 KRX→AL로 바뀌어 있다. 지금 41일을 돌리면:
- KRX 전용으로 돌려도 기준선 드리프트 때문에 60분 겹침구간이 기존과 안 맞고,
- `MINUTE_STORE=al`을 켜면 아예 다른 데이터 소스라 처음부터 비교 대상이 아니고,
- 기존 60분 아카이브 41개 중 5개(0702~0708)는 이미 오늘자로 갈아끼워져 있어
  나머지 36개와도 서로 균일하지 않다.

## 원상복구 조치
- `results/rank_timeline_20260701.json`: 백업(`.bak60`)에서 복원 완료 —
  score 52.7(원본과 일치하는 값)로 되돌려놨다. 다만 **위에서 발견한 것처럼
  이 파일이 08-29 원본과 완전히 동일한지 100% 장담은 못 한다** — 이번
  세션 안에서 최소 한 번 이상 write가 일어난 뒤 복원한 것이라, 혹시 모르니
  0701 하나는 나중에 별도로 재검증(가능하면 08-29 시점 백업이 어딘가 있는지
  확인) 권장한다.
- `results/rank_timeline_full_20260701.json`(15:30 확장 테스트 산출물)과
  임시 비교 파일은 삭제 완료 — 산출물 남기지 않음.
- 0702~0708(오늘 19:18~19:20에 이미 바뀐 5일)은 **내가 만든 게 아니라
  건드리지도 않았다** — 원상복구 대상이 아니라 그대로 뒀다. 다만 위 이유로
  "기존 60분 아카이브"의 일부가 이미 오늘 코드/데이터로 재생성돼 있다는 사실
  자체가 lead가 알아야 할 정보라 그대로 보고한다.
- 코드 파일(rank_archive.py 등)은 전혀 건드리지 않았다 — 발견한 미커밋 변경은
  내가 만든 게 아니라 기존에 이미 그 상태였다.

## lead 판단이 필요한 것
1. `rank_archive.py`/`rank_timeline.py`/`replay.py`/`universe.py`의 미커밋
   KRX→AL 마이그레이션 — 완료해서 커밋할지, 되돌릴지. 이게 정리되기 전엔 이
   레포의 어떤 재생성도 "재현 가능"하지 않다.
2. 참조 데이터(themes.csv 등)가 08-29 이후 갱신된 게 의도된 일상 운영(예:
   장 시작 전 자동 prepare)인지, 위 마이그레이션 작업의 부산물인지 — 후자라면
   원래 08-29 스냅샷을 복구할 방법이 있는지부터 확인 필요.
3. 41일 확장을 **KRX 전용(기존과 같은 소스)으로 만들지, 아니면 이 기회에
   통합(AL)으로 만들지** — 마이그레이션이 이미 진행 중이라면 지금 KRX로
   만들어봐야 곧 다시 만들어야 할 수 있다.
4. 위 조건들이 정리되면 재개하겠다 — 그때는 **41일 전체를 한 번의 일관된
   상태**(코드 커밋 완료 + 참조 데이터 고정)에서 처음부터 다시 만드는 걸
   권한다(60분/15:30 두 아카이브를 같은 배치에서 함께 생성하면 이런 드리프트
   문제 자체가 원천 차단된다).
