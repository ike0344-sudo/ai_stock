# 큐 처리 중 발견: 테마순위 3축 재측정이 최근 보류 지시와 충돌 — 판단 요청

## 무슨 일이 있었나
`state/agent_queue/backtest-agent.md`의 "테마순위 3축 재측정"(41일 재정비본,
오염 제외 없이 전량) 항목을 순서대로 집어 착수 준비를 하던 중, 착수 전
데이터부터 검증하는 과정에서 **STATUS.md의 strategy-agent 행에 이 항목과
직접 충돌하는 최근 기록**을 발견했다:

> strategy-agent(2026-09-01 01:05): "lead 지시(0100) — **3라운드 보류,
> 사용자 판단 대기.** 두 라운드(틱/일봉) 연속 전부 기각, '갭이 전부다'
> 결론이 두 번 독립 확인됨. 지시대로 새 가설 안 만들고 유휴 전환."

**"3라운드"가 정확히 이 큐 항목(테마순위 재측정)을 가리키는 것으로 보인다**
— 지금까지 순서: 1라운드(틱, 테마순위 3축, 잠정) → 2라운드(일봉 3축) →
이 큐 항목이 "테마순위 3축 재측정"이니 시간순으로 3번째 라운드와 일치한다.

## 검증 없이 안 진행함 — 대신 확인한 것
1. **큐 항목 자체(41일 균일 재생성)는 실제로 준비돼 있다** — 직접 mtime
   전수 조회로 41개 파일이 08-31 23:10:39~23:14:26 사이 한 배치로
   재생성됐음을 확인, `rank_timeline_full_*.json`(15:30본) 41개도 존재
   확인. **196170(알테오젠) lead_pct 이상도 실제로 해소됐음을 직접
   확인**(이전 28회 등장·20~40%대 → 이번 5회·-6.2~8.6% 정상 범위, 직접
   재검색). 즉 **데이터 자체는 재측정할 준비가 돼 있다.**
2. 그런데 **lead가 이미 이 재측정("3라운드")을 보류하고 사용자 판단을
   기다리라고 지시한 기록이 있다.** 이 지시가 큐 항목보다 최신이거나
   최신이 아닌지, 큐 항목이 그 보류 지시를 반영해 갱신된 것인지 확인할
   방법이 나(backtest-agent)에게는 없다 — 큐 파일 자체엔 보류 표시가
   없다.

## 판단을 요청하는 이유
이번 지시("안 뽑은 항목 1건, 순서대로 시작해라")는 명시적이고 직접적이라
그대로 따르는 게 원칙이지만, **바로 위 STATUS.md에 "이 작업을 보류하고
사용자 판단을 기다리라"는 lead 지시가 최근 기록으로 남아 있는 걸 보고도
모른 척 진행하는 건 위험하다고 판단했다** — 지시서의 "모호하거나 위험하면
하지 말고 파일로 써서 lead에 물어라"에 해당한다고 본다. 두 가지 가능성이
있다:
1. 방금 받은 지시가 그 보류를 해제하는 새 판단이다(사용자가 이미
   "3라운드 진행"으로 결정했고, 이 큐 실행이 그 실행 신호다) → 그렇다면
   바로 착수하면 된다.
2. 보류가 아직 유효한데 큐 파일이 미처 안 갱신된 상태에서 순서대로
   처리하다 우연히 걸렸다 → 그렇다면 지금 돌리면 안 된다(이미 두 번
   같은 결론이 나온 걸 세 번째로 반복하는 게 무의미할 수도 있고, 사용자가
   다른 방향을 정하는 중일 수도 있다).

**코드 준비는 이미 해뒀다** — 기존 `theme_rank_prereg_measure.py`에
`is_dates_valid(exclude=True)`/`oos_dates_valid(exclude=True)`처럼 옵션
매개변수를 추가해 `exclude=False`로 41일 전부(제외 없이) 돌릴 수 있게
해뒀다(기존 기본값은 그대로라 이전 리포트 재현성은 안 깨짐, 기존 테스트
8건 그대로 통과 확인). **판단만 내려주면 몇 분 안에 돌릴 수 있다.**
