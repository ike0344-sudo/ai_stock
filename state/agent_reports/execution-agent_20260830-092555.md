# execution-agent 보고 (2026-08-30 09:25) — 큐 항목 3/4: 주문 실패 시나리오 정리

## 1. 부분체결
**지금 동작**: `check_fill`(`order_execution.py:296-338`)이 매 사이클 잔량을
읽어 증분만 `record_position_opened`/`record_position_added_to`(매수) 또는
`record_partial_exit`(매도, `trading_loop.py:process_pending_orders_once`)로
반영. 정상 케이스는 막혀 있음.
**안 막힌 것**: `ord_no`가 목록에서 사라지면 무조건 "전량체결"로 간주(`:318-321`)
— 거래소가 잔량을 우리 요청과 무관하게 만료/거부해 사라진 경우(IOC 등)와 구분
못 함. 실제 체결량보다 많이 기록될 수 있음. 잔량 필드명도 미검증(큐 2번과 동일
근본원인) — 틀리면 `status="unknown"`으로 멈추고 filled_qty가 영원히 0에 머무름
(`:324-327`).

## 2. 타임아웃 취소 실패
**지금 동작**: `cancel_if_timed_out`(`:341-` 이하)이 예외 또는 `return_code!=0`
둘 다 상태를 안 바꾸고 반환 → 다음 사이클에 자동 재시도(자연스러운 백오프 효과).
**안 막힌 것**: 재시도 횟수 상한이 없음 — 브로커가 계속 거부(예: 그 사이 이미
체결돼 "취소할 게 없음" 응답)해도 영원히 재시도만 하고, 이 케이스는
`notify_error` 대상(`ambiguous`/`unknown`만 알림, `process_pending_orders_once`
:428 부근)이 아니라서 **사람에게 알림이 안 감**. 조용히 매 사이클 헛도는 상태로
남을 수 있음.

## 3. 재시작 중 미체결
**지금 동작**: `restore_pending_orders_from_broker`가 시작 시 1회, 우리 로그
(ord_no 매칭)와 브로커 응답을 대조해 확인된 것만 복원.
**안 막힌 것**: (a) 로그 파일 자체가 유실/손상되면 조용히 0건 복원 — 그 주문은
영원히 고아가 됨. (b) `reconcile()`은 시작 시 1회만 돈다 — 복원 실패한 미체결이
나중에 장중에 체결돼도, 그 사실을 잡아줄 두 번째 안전망(주기적 재대사)이 없음.

## 4. API 응답 지연

**안 막힌 것**: 딱히 없음 — 이 항목은 기존 설계로 충분하다고 판단.
