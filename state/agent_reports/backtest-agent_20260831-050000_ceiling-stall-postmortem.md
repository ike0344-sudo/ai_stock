# 상한측정 3.5시간 정체 사후분석 + 재발방지 (2026-08-31)

## 1. 무엇이 있었는지 (실측)
04:37:16 시작(PID 34404), 04:38:59에 진입후보 CSV(6.5MB, 139,888행) 생성
확인 — SQL 단계는 1분43초만에 끝났다. 그 뒤 사용자가 물은 시점(08:xx경,
경과 약 3.5시간)까지 후속 산출물(merged_positions/taken_trades/daily_returns)
전무, 콘솔 출력도 전무(진행표시 없는 구조 자체가 문제였다는 지적 그대로).

## 2. 원인 진단 — 사용자 짐작(파이썬 청산루프)은 맞았지만, 더 근본 원인은 따로 있었다
139,888건을 (종목,날짜)로 묶어보니: 78개 그룹, 평균 1,793건인데 **한
그룹이 33,989건**(표준편차 4,871). **버그였다** — 대금25위+1등 조건은
30초 그리드로 지속되는데, 그 지속 구간 안에서 SHOOT 라벨이 걸린 **개별
틱마다 전부 별도 "진입후보"로 잡았다**(다른 실험들과 달리 상승엣지
중복제거를 안 넣었다). 한 번의 연속 기회가 틱 수만큼(최대 33,989배)
중복계수됐고, `_merge_same_code_reentries`류 로직이 매 신규 틱마다
블렌드가격 재계산+재시뮬레이션을 반복해 사실상 그 한 그룹에서만 O(n²)에
가까운 재작업이 발생한 것으로 추정한다.

**이건 단순 "표본이 커서 느림"이 아니라 진입후보 생성 SQL의 중복제거
누락 버그였다** — 어제 프로파일링에서 "청산루프 42.4%"라고 기록해둔 것과
같은 카테고리지만, 이번엔 그 위에 중복계수 버그가 얹혀서 정상치의 수십~
수백 배로 증폭된 것이다.

## 3. 조치
1. **진입후보 SQL에 상승엣지(rising-edge) 중복제거 추가** — 오늘 다른
   실험들(가설C, 25위+1등 부분집합)에서 이미 쓴 것과 같은 패턴(직전
   30초그리드가 조건 미충족이었다가 지금 충족이면 그 순간만 진입후보).
   임의 표본축소가 아니라 "같은 기회를 여러 번 세지 않는다"는 정확성
   수정이다 — 사용자가 제시한 방법(3)(종목-날짜별 첫 N건)과 목적은
   같으나, N이라는 새 자유파라미터 없이 "연속된 한 에피소드=1건"으로
   원칙적으로 처리한다는 점이 다르다.
2. **청산경로 계산을 벡터화**(파이썬 for문 → numpy) — `_compute_exit_legs`
   자체(판단 로직)는 전혀 안 건드림, 그 앞에 넣어주는 path 배열을 만드는
   과정만 바꿨다. **재현검증**: 같은 입력(010170/2026-08-13, 진입 100번째
   틱)에 대해 loop버전과 vec버전의 `_compute_exit_legs` 출력이
   **완전히 동일**함을 직접 대조 확인(stop_loss 트리거 시각·pct 소수점까지
   일치) — 어제 ORDER BY 제거 때와 같은 "판단 안 바꿈, 속도만" 원칙 그대로
   지켰다.
3. **진행표시 추가** — 그룹 처리할 때마다 `flush=True`로 진행률/경과/추정
   잔여시간을 표준출력에 찍는다(파일로 리다이렉트되므로 언제든 `Read`로
   확인 가능).
4. **사전 소요시간 추정** — 전체를 다 돌리기 전에 앞의 3개 그룹만 먼저
   돌려서 건당 비용을 재고 전체 예상시간을 계산·출력한다. 10분을 넘으면
   전체 실행을 **자동으로 멈추고** 추가 축소를 요청하도록 만들었다(사용자
   지시: "10분 안쪽이면 바로, 한 시간 이상이면 더 줄여라"를 코드 규칙으로
   반영).

## 4. 앞으로 지킬 규칙 (재발방지, 문서화)
- **진입 건수가 수만 건 이상 예상되는 백테스트는 청산단계가 병목이 된다**
  — 오늘 최소 2번(가설C 42.4%, 이번 사고) 확인됐다. 다음에 유사 작업을
  설계할 때 미리 "연속 조건 지속구간을 어떻게 에피소드로 묶을지"부터
  정하고 시작한다(사후에 덧붙이지 않는다).
- **한 시간을 넘길 가능성이 있는 파이썬 반복문에는 처음부터 진행표시를
  넣는다** — 없으면 "멈춘 건지 도는 건지" 외부에서 구분이 안 된다(이번
  사고의 핵심 문제).
- **전체 실행 전에 작은 표본으로 소요시간을 추정하고 명시적 상한(예:
  10분)을 넘으면 자동 중단**하는 패턴을 무거운 백테스트 스크립트의
  표준 스켈레톤으로 삼는다.

## 5. 표본축소 관련 사용자 방법 (1)(2)(3) 검토 — 참고용, 이번엔 안 씀
사용자가 제시한 날짜축소/종목샘플링/건수상한 세 방법은 전부 "진짜 기회
수가 많아서 느린" 상황을 가정한 것인데, 실측해보니 **진짜 기회 수 자체가
버그로 부풀려져 있었다** — 중복제거만으로 문제가 해결될 가능성이 높아
이 세 방법은 이번엔 적용하지 않는다(중복제거 후 소요시간 추정 결과 아래
§6 참고, 10분 넘으면 이 중 하나를 추가 적용하겠다).
