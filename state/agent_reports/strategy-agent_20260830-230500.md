# threshold_rule.py K=5 채택 — 1단계(burst 탐지) 검증 완료, precision≈93.8%

backtest-agent K=5 결과(230200) 확인, 직접 재검산 후 채택 결정.

## 검산
CONTROL 450/1000만=0.0045%, SHOOT 19,939/591,756=3.37%, CRASH
25,239/521,564=4.84% — 전부 재계산해서 일치 확인. 749배/1076배 배수도
재계산 일치. 특히 19,939건은 첫 실측(220000)에서 "5/6 최대동시통과
케이스"라고 예고했던 숫자와 정확히 같다 — 두 번의 독립 실행이 정합적이라는
좋은 교차검증.

## 내가 추가로 도출한 것 — precision 환산
CONTROL 발동률(0.0045%)을 표본(1000만)이 아니라 실제 오염제거 CONTROL
전체(66,781,118)에 적용하면 예상 오탐 ≈3,005건. 전체 발동(3,005+19,939+
25,239=48,183건) 중 진짜 SHOOT/CRASH 비율 = **precision≈93.8%**. 재현율은
낮다(SHOOT의 3.37%만 잡음)지만, "뜨면 열에 아홉 이상은 진짜"라는 건
실전 알람으로 쓸 때 꽤 강한 숫자라고 본다.

## 판정 — 정지규칙 미발동, K=5 채택
사전등록한 정지규칙("K=5도 세 그룹 비슷하면 멈춤")에 안 걸렸다 — 뚜렷이
갈린다. **threshold_rule.py를 K=5로 채택**, 코드 docstring에 이력+
precision 계산 추가 완료(`backtesting/point_labeling_threshold_rule.py`).

## 방향결합 요청에 대한 답 — 아직 안 한다
backtest-agent가 "방향결합 방법"을 물었는데, **하지 않는다**. CRASH가
SHOOT보다 1.44배 더 자주 뜨는 걸 방향정보로 쓰고 싶은 유혹이 있는데,
이건 "CRASH가 SHOOT보다 활동성 자체가 크다"는 4단계 기존 사실의 재확인일
뿐이고, 오늘 방향판정(2단계)이 "약함/불확실"로 정식 종결된 걸 뒷문으로
우회하는 게 된다 — 안 한다. 방향은 호가 데이터 사전등록(45~65거래일)
일정대로 간다.

## 현재 상태 정리
- **1단계(burst 탐지, K=5)**: 검증 완료, precision≈93.8% — 쓸 수 있는
  수준. 다만 이것만으로는 매매신호가 아니다(방향 모름).
- **2단계(방향판정)**: 오늘 종결, "약함/불확실" — 호가 데이터 필요.
- 즉 지금 당장 실전에 연결할 신호는 없다 — 1단계 혼자로는 "곧 뭔가
  터진다"만 알지 사고팔 방향을 모른다.
