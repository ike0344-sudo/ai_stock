## 1) look-ahead 여부

### 원본 파이프라인
`kospi-theme-engine/rank_archive.py` → 종목당 `rank_timeline.py --date=YYYYMMDD`를
서브프로세스로 호출 → `results/rank_timeline_{날짜}.json`에 저장. **아티팩트가 아니라
이 JSON이 진짜 원본**이고, 아티팩트(byDay)는 이걸 top5/chgtop 형태로 가공한 표시물이다
(rank_timeline.json의 frame 스키마는 `{t, chgtop, rows[]}`뿐 — "top5"라는 키 자체가
없다, top5는 rows를 잘라 만든 것).

### 파일 생성 시각으로 확인한 사실: 전부 배치 재계산본, 실시간 기록 아님
`results/rank_timeline_*.json` 41개 전부 **2026-08-29 20:11~20:22** 사이에 한 번에
생성됐다(`ls -la` mtime 확인, `results/arch_all.out` 로그와 정확히 일치 —
`rank_archive.py --all` 1회 실행). 즉 09:01분 시점에 그 값이 실시간으로 기록된 스냅샷이
**아니다** — 2026-08-29 저녁에 저장된 분봉(`data/stocks/minute/*.csv`)을 되감아
계산한 결과다. (예외 1건: `rank_timeline_20260813.json`만 2026-08-30 11:15에 개별
재생성됨 — 아래 "예외" 참고.)

이게 "못 쓴다"를 뜻하진 않는다 — `rank_timeline.py`는 매 분 프레임을 만들 때 **그
시각까지의 봉만** 소비한다(코드 136~153행, `cursor`가 앞으로만 밀리고 `s <= cursor`인
봉은 건너뜀). 즉 09:05 프레임을 만들 때 09:06 이후 가격은 절대 안 본다 — **가격·시각
축의 look-ahead는 없다.** `subscribed(day=...)`(구독 종목 산출, replay.py 38~75행)도
그 날짜 **직전 5거래일** 일봉만 쓴다(`d.index < stamp` 필터, 61행) — 이것도 인과적.

### 실제로 있는 look-ahead 2가지 (둘 다 "그날 하루 안"이 아니라 "여러 날에 걸친 기준값"이 균일 적용되는 형태)

**(a) flow_speed(14/100점)의 기준선(profile_theme.csv)이 미래 데이터로 만들어짐.**
`app/reference/baseline.py`의 `build_rows()`는 `LOOKBACK=20`으로 **분봉 파일에 있는
가장 최근 20거래일**을 쓴다(`days = sorted(daily)[-lookback:]`, 97행) — "그 날짜 이전
20일"이 아니라 "지금 시점 기준 최근 20일"이다. 이 프로파일 파일 하나가 41일 replay
전체에 공유되므로, 07-01 프레임의 flow_speed도 8월 말 근처 20일로 만든 기준선과
비교된다. 07-01 시점엔 존재하지 않았던 정보다. 다만 이 기준선은 **테마마다 고정된
상수**라 날짜별로 다르게 왜곡되진 않는다(모든 날 같은 기준선을 쓰므로 날짜간 상대
비교엔 영향이 적고, 절대 스코어 해석에만 영향).

**(b) 테마 구성종목(themes.csv)이 "지금" 스냅샷 하나뿐, 날짜별 버전 없음.**
`app/reference/store.py:load_reference()`가 읽는 `THEMES_FILE`은 날짜 구분이 없는
단일 파일이다. 즉 07-01 replay도 **오늘 기준 테마 편입 상태**로 계산된다. 테마
구성종목이 그 사이 편집됐다면(그룹 통합·종목 추가/제외 등, 실제로
`min_stocks: 4->3` 같은 변경이 08-22에 있었음 — 아래 2번) 07-01 시점엔 없었던
구성으로 재현되는 것.

둘 다 "그 시각 이후 가격을 미리 본다"는 강한 의미의 look-ahead는 아니고, "지금 알고
있는 것을 과거에 투영해 재현한다"는 종류다 — replay.py 자체 docstring도 이게 목적임을
분명히 밝힌다("**채점은 그대로 쓴다**... 과거 분봉을 흘려 넣어 그 시각의 표를
재현한다"). 전략 리서치에서 "과거 그날 실제로 화면에 뜬 값" 대신 "지금 로직을 과거에
적용했으면 어땠을까"로 취급해야 한다는 뜻 — 이 구분을 리포트에 명시하지 않으면 결과가
과대해석될 수 있다.

**예외**: `rank_timeline_20260813.json`은 나머지 배치(08-29 20:xx)와 달리 다음날
08-30 11:15에 별도로 재생성됐다. `config.yaml`/`app/engine/scoring.py`/
`app/engine/runner.py` 커밋 로그로 그 사이(08-29 20:00~08-30 12:00) 배점·로직 변경이
없었음은 확인했다(git log 조회, 커밋 0건) — 워킹트리에 커밋 안 된 임시 변경이 있었을
가능성까지는 배제 못 하므로, 이 날짜를 핵심 근거로 쓰는 결론이 나오면 다른 이웃 날짜와
스팟체크 권장.

### 참고: 알려진 유사 함정은 이 경로에 없음
`kospi-theme-engine/CLAUDE.md`가 경고하는 `subs_cached()`(전날 구독을 고정해 라이브의
`always_top` 실시간 교체를 놓치는 함정)는 `chgtop_*.py` 계열 스크립트가 쓰는 것이고,
`rank_timeline.py`는 자체 `swap()` 함수로 분마다 라이브와 같은 동적 교체 규칙을
재현한다 — 이 함정은 해당 없음.

## 2) 2026-08-22 점수 기준 변경의 영향

### 변경 사실 확인
`git show fcdb756 -- config.yaml` (커밋 시각 2026-08-23 22:34, diff 주석에
"2026-08-22 재구성"이라 명시) — 실제로 아주 큰 변경이었다:

- **배점 자체**: `share_ratio`(11)·`relative_volume`(9) = 20점 완전 제외(0점),
  `value_rank` 22→30, `rise_strength` 20→27, `value_share` 13→18, `flow_speed`
  12→14, `rising_ratio` 7→8, `new_high` 6→3
- **순위 산출식도 바뀜** (질문에서 우려한 부분, 사실로 확인됨): `value_rank_cap`
  2.0(자리 가중합 기준)→3.0(**개수** 기준), `value_rank_weights` `[]`(1위=1.00 ~
  20위=0.05 선형 가중)→`[1]*20`(평탄 — 20위 안이면 순위 무관 1개로 침). 즉 예전엔
  "대금 1위 안에 얼마나 상위에 있는가"였는데 지금은 "대금 20위 안에 몇 개 있는가"로
  개념 자체가 바뀌었다.
- 부가로 `min_stocks` 4→3, `value_rank_min_chg`/`value_rank_chg_full`
  신설(등락률로 대금순위 자리 값을 깎는 보정) 등도 같은 커밋에 들어감.
- 뒤이은 `e76e6ec`(08-28)은 주석만 고친 정정 커밋 — 코드/배점 자체 변경은 없음
  (배점을 옛 값 45점·32점으로 잘못 설명한 주석 4곳을 고침).

### 41일 아카이브에 미친 실제 영향 — 없음 (레짐 분할 안 됨)
질문의 우려("07-01~08-21과 08-22~08-28의 score가 같은 척도인가")는 **원천적으로
해당 없다** — 1번에서 확인했듯 41일 JSON **전부**가 08-29 저녁에 **현재(=08-22 이후)
배점 하나로 일괄 재계산**됐다(`--all` 배치 1회 실행, 예외 1일 제외 로직 변경 없음
확인). 즉 아카이브 안에는 옛 배점으로 계산된 프레임이 하나도 없다 — score/rank 전부
동일 척도, 동일 순위식이다. IS/OOS를 707-01~08-21 vs 08-22~08-28로 나눠도 그 경계가
배점 레짐 경계와 겹치지 않는다(애초에 archive에 옛 배점 구간이 없으므로).

다만 이건 1번의 (b)와 같은 맥락에서 "실제 그날 화면에 떴던 값과 다르다"는 의미이기도
하다 — 07-01 실제 라이브 화면은 옛 배점(45/32점 체계)으로 표시됐었는데, 지금 아카이브의
07-01은 새 배점으로 재현된 값이다. "일관된 하나의 함수로 41일을 본다"는 백테스트
목적에는 오히려 유리하지만, "그날 트레이더가 실제로 뭘 봤는가"를 재현하려는 목적이면
안 맞는다 — 어느 쪽을 쓸지는 전략 설계 단계에서 lead/strategy-agent가 정할 문제.

## 추가 확인

**결측일**: 없음. `rank_archive.trading_days()`(분봉 quorum≥35 기준 실제 거래일
목록)로 계산하면 07-01~08-31 사이 거래일이 42일인데, 아카이브/아티팩트는 41일
(07-01~08-28)로 정확히 오늘(08-31, 진행 중이라 당연히 제외)만 빠진 상태 — 그 사이
빠진 거래일 없음. 부분결측도 없음: 41일 전부 `times` 60개, 테마별 `rank`/`score`
배열 60개, `top5`/`chgtop` 60개로 완전(전수 검사, 이상 0건). 테마 개수는 날짜별
22~23개로 소폭 변동하는데 이건 결측이 아니라 `min_theme_stocks`(3개 미만 테마 제외)
게이트가 그날 종목 수에 따라 자연스럽게 갈리는 것.

**아티팩트보다 원본에 더 있는 것**:
- **09:01~10:00 이후 시간대**: 원본 분봉(`data/stocks/minute/*.csv`)엔 하루 전체가
  있다. `rank_timeline.py --to=15:30`처럼 인자만 바꾸면 코드 수정 없이 정규장 끝까지
  확장 가능 — 지금 아카이브가 60분만 저장해뒀을 뿐, 데이터 자체의 한계는 아니다.
- **테마 구성종목 원본**: `data/reference/themes.csv`(store.py가 읽는 THEMES_FILE)에
  종목→테마 전체 매핑이 그대로 있다. 아티팩트엔 순위/스코어만 있고 "그 테마가 어떤
  종목들로 구성됐는지"는 없는데, 원본엔 있다.
- **`highs`(신고가) 필드는 원본 아카이브에 아예 없다** — `rank_timeline.json`의 frame
  스키마는 `{t, chgtop, rows}`뿐이라 highs 자체가 없는 필드다. 신고가 판정 로직은
  `app/ui/models.py`(4단계 색 분류)와 `replay.py`의 `_month_highs`에 존재하지만,
  이걸 41일치로 미리 뽑아 archive에 붙이는 배치 스크립트는 이 레포에서 못 찾았다.
  `data/stocks/daily`의 장기 이력으로 재계산은 가능해 보이나(신고가 판정 자체가 일봉
  이력 기반), 지금 아티팩트의 highs 배열이 정확히 어떤 코드로 만들어졌는지는 이번
  감사로 특정 못 했다 — highs를 신호로 쓰려면 생성 스크립트부터 새로 짜야 한다.
- **거래대금 원자료**: rank_timeline의 `day_tv`/`market_rank`는 분봉(close×volume)
  파생치이지 KRX 실시간 거래대금 TR(ka10032) 원본 응답을 저장해둔 게 아니다 — 라이브
  전용, 미보관. 재현은 분봉 기반 근사치로만 가능(현재 아카이브가 이미 하는 방식).

## 확인 방법
전부 코드 열람 + 파일 시스템 조회(`ls -la` mtime, git log/show, python으로 JSON
직접 파싱)로 확인했다. 추측 없음. 원본 파일은 읽기만 했고 수정하지 않았다.
