## 1차 검증에서 발견한 불일치 — 원인 규명하고 고쳤다
- 유닛테스트(day 경계 케이스 포함) 6개는 처음부터 통과했지만, **실측 1045종목
  전수 대조에서 32종목 34행이 불일치**했다(사용자 지시대로 원본이 맞다고 가정하지
  않고 직접 대조).
- 원인: 등락률이 임계값(1.5%)에 **정확히** 걸치는 극소수 경우, pandas의
  `pct_change()`는 `close/close_ref - 1`로 계산하는데 내가 처음 짠 SQL은 수학적으로
  같은 `(close-close_ref)/close_ref`로 짜서 부동소수점 반올림이 갈렸다. 실측: 105/7000,
  105/6000 두 케이스 모두 `a/b-1` = 0.014999999999999902(미달), `(a-b)/b` = 0.015
  정확히(충족) — 같은 숫자인데 계산 순서에 따라 임계값 위/아래로 갈리는 진짜
  부동소수점 이슈였다(로직 버그 아님).
- 조치: SQL을 pandas와 똑같은 순서(`close/close_ref - 1`)로 맞춤. **재검증 결과
  1045종목 전부 완전 일치(불일치 0), 총 엔트리 수도 52,934건으로 정확히 같음.**
- 삽질 하나 더: 이 과정에서 SQL 안에 한글 주석을 직접 넣었다가 Edit 도구가 그 부분만
  다른 인코딩으로 써서 파일이 깨져 DuckDB 파싱 에러가 났다(다른 부분은 멀쩡했음).
  한글 설명은 SQL 문자열 밖, 쿼리 생성 직전의 파이썬 `#` 주석으로 옮겨서 해결 —
  앞으로 f-string으로 만드는 SQL 안에는 비ASCII 주석을 넣지 않는 게 안전하다.
