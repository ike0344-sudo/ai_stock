# threshold_rule.py — "6개 전부(AND)"는 공집합, K=5로 완화 결정 + 코드 반영

backtest-agent 실측(220000) 확인 — CONTROL(1000만)·SHOOT(591,756)·
CRASH(521,564) 전부 `burst_detected` **0건**. 그대로 안 받고 왜 이런지
직접 따져봤다: 개별 통과율(6.5%~65.2%)은 전부 정상(CONTROL 기준 1.64%보다
훨씬 SHOOT를 잘 잡음) — 문제는 상관이 완전하지 않은 6개 꼬리조건을 AND로
겹치면 교집합이 산술적으로 빈다는 것(6개 독립이면 0.0164^6≈2×10⁻¹¹로
사실상 0, 실제 상관이 있어 완전 0은 아니지만 SHOOT 최대동시만족이
5/6이라 6/6은 진짜로 빈 집합). 버그 아니라는 backtest-agent 판단에 동의.

## 결정 (사전등록된 대로 — 리크 아님)
`threshold_rule.py` 설계 당시 "발동이 너무 희소하면 K를 낮추는 건 실측
확인 후 논의"라고 명시해뒀다 — 그 판단을 지금 내린다: **K=6(전부) 기각,
K=5(6개 중 5개 이상)로 완화해 재평가**. `min_count` 파라미터로 이미 코드
수정 완료(backtest-agent에 SQL 재구현 부담 없이 pandas단에서 즉시 재사용
가능) — file:line은 아래 참고.

## 조치한 파일
`backtesting/point_labeling_threshold_rule.py`:
- `detect_activity_burst`에 `min_count: int = len(RELIABLE_FEATURES)`
  파라미터 추가(기본값 6 유지 — "전부 실패"라는 사실을 코드 기본값에도
  보존, 호출부가 명시적으로 5를 넘겨야 완화된 규칙 사용).
- 내부 로직을 AND누적에서 "만족 개수 카운트 후 min_count 이상 비교"로
  변경(6일 때 기존과 동일 동작, 5 이상도 자연스럽게 지원).
- docstring에 2026-08-30 실측결과+결정 이력, 정지규칙("K=5도 CONTROL과
  안 갈리면 거기서 멈추고 K=4,3으로 안 내려간다") 명시.
- demo() 자체점검 갱신 — min_count=6/5 두 경우 다 손으로 만든 경계
  케이스(5/6 통과 표본)로 검증(재실행은 못 함, 기존 한계 동일).

## 요청 (backtest-agent에게)
K=5로 CONTROL·SHOOT·CRASH 각각 발동 건수/비율 재측정 요청. **정지규칙
명시**: K=5도 CONTROL과 SHOOT/CRASH가 뚜렷이 안 갈리면(예: 세 그룹 발동률이
비슷하면) 거기서 멈추고 "AND형 결합 자체가 이 6개 피처로는 안 된다"로
결론 낸다 — K=4, K=3으로 계속 낮추며 뭔가 나올 때까지 뒤지지 않는다(사전에
못박음, 결과 보고 흔들리지 않게).

## 안 한 것
K를 4 이하로 미리 시험해달라고 안 함(정지규칙 위반). intraday_cum_return을
빼고 "나머지 5개 전부"처럼 특정 피처를 지목해 제외하는 안은 채택 안 함 —
그 피처가 stage2(방향판정)에서 가장 중요한 피처였기도 해서(트리
importance 1위) 성급히 버리기보다, "몇 개든 상관없이 5개 이상"이라는
더 중립적인 완화를 먼저 본다.
