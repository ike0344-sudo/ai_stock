200종목 구독 목록 자체는 입력이 아니라 배경일 뿐 — 저장 여부는 오직 저 두 조건.

## 3. 순위 재사용 지점 — 이미 있는 엔진 state, 새로 안 만듦
코드로 확인: `app/engine/runner.py`의 `Engine.swap_in()`이 매 폴링 주기마다
`self._market_rank = self._rank_of(today)` (688~699행)로 이미 "그 시점 거래대금
순위" 딕셔너리(`code -> rank`)를 갱신해 들고 있다. 이 값을 부르는 폴링 루프는
`app/main.py:start_index_poller`의 `run()`이며, 매 사이클 `client.trading_value_top()`
(ka10032)을 호출해 `engine.swap_in(top)`을 부른다.

**주의할 것 하나**: 사용자는 "10초마다"라고 했는데, 코드로 확인한 실제 주기는
`poll_interval()` 기준 **평소 30초(INDEX_POLL_SEC), 개장 직후(08:45~09:10)만
20초(OPEN_POLL_SEC)** 다 — 10초가 아니다. 검증 없이 10초로 받아쓰지 않고 이 차이를
그대로 보고한다. 순위 신선도가 최대 30초 지연될 수 있다는 뜻이라 설계에 반영해야
한다(경계 근처 짧은 급변은 다음 폴링까지 놓칠 수 있음 — 아래 6번과 연결).

**구현 방식**: `self._market_rank`는 private다. 외부(저장 훅)에서 직접 접근하지
않고, `Engine`에 `get_market_rank(code: str) -> int | None` 같은 공개 접근자
메서드를 하나 추가해 그걸 통해서만 읽는다(캡슐화 유지, 최소 diff). 같은 프로세스
안에서 직접 호출이라 HTTP(`/api/market`) 왕복 없이 즉시 조회 가능 — 매 체결마다
불러도 비용이 사실상 0에 가깝다.

## 4. 히스테리시스 — 넣지 않는 것을 권고 (판단, 근거 아래)
요청받은 그대로 판단한다: **권고는 히스테리시스 없이 단순 `<=35` 문턱, 대신
순위 이력을 별도의 아주 가벼운 로그로 남기는 쪽.**

- 히스테리시스(35 진입/45 이탈)의 장점은 인정한다 — 경계에서 흔들리는 종목의
  파일이 끊겼다 이어졌다 하는 걸 줄인다.
- 하지만 사용자가 지적한 "진짜 문제"(구멍이 데이터 없음인지 순위 밖인지 구분
  안 됨)는 **행에 순위 컬럼을 남기는 것만으로는 못 푼다** — 그건 "기록된 행"에만
  붙는 정보라, "기록이 아예 없는 구간"의 이유는 여전히 설명 못 한다. 이 문제를
  실제로 푸는 건 순위 이력 자체를 별도로 남기는 것이지 히스테리시스가 아니다.
- 순위 이력을 폴링 주기(20~30초)마다 아주 작은 파일로 남기면(예: `code,rank,ts`
  몇 줄, 200종목×하루치라 해도 수 MB 이내) **모든 시점의 순위를 그대로 재구성**
  할 수 있어, 히스테리시스보다 더 정확하게(이진 상태가 아니라 실제 순위 궤적)
  "왜 이 구간엔 호가가 없는지" 설명된다.
- 히스테리시스를 넣으면 자유 파라미터(45)가 하나 늘고, 그 값을 정당화할 근거가
  아직 없다(35의 1.3배쯤이라는 것 외엔 임의적). **판단: 안 넣는다.** 대신 순위
  이력 로그를 추가한다(신규 소형 파일 하나, 기존에 없던 걸 새로 만드는 비용은
  있으나 훨씬 단순하고 정보량이 많다).
- 이견 있으면 쉽게 뒤집을 수 있는 결정이다 — 실제 운영해보고 "구간이 자주 끊겨
  분석이 어렵다"는 게 실측되면 그때 히스테리시스를 추가하는 게 순서상 맞다고 봄.

## 6. 용량 재추정 (200종목 → 동적 top35-2, 실측 기반 하향식 계산)
이전 보고(210451)의 200종목 추정(20~50MB/일)은 근거가 약한 placeholder였다 —
이번엔 오늘 실측한 우리 틱 데이터로 바닥부터 계산한다.

- 실측: KRX전용 117종목×18일 체결 압축본 386MB → 종목·일 평균 **약 183KB/종목·일**
  (체결만, 컬럼 2~3개 기준)
- 동적 top35에서 005930/000660을 뺀 상태로는 **한 시점에 최대 33종목**만 조건을
  통과 — 하루 내내 이 33개 "슬롯"이 채워져 있다고 가정하면(회전은 있어도 총
  점유는 거의 상시) 하루 점유량은 대략 "33종목·일"에 준함
- 10단호가는 컬럼이 체결 대비 약 14배(40여개 vs 2~3개) — 압축이 더 잘 먹을
  걸로 보이나 보수적으로 **체결 압축본의 5배**로 가정
- 소피증권은 `_AL`(통합) 기본 구독이라 NXT 포함 — 오늘 실측한 NXT 비중(중앙값
  약 40% 추가)을 반영해 ×1.4
- 계산: 183KB × 33 × 5 × 1.4 ≈ **42,000KB ≈ 41MB/일**
- 한 달(21거래일) 기준 **약 0.86GB/월**
- **005930/000660 제외 효과**: 이 둘은 평소 거래대금 최상위 상시권이라 순위
  상으로는 제외해도 다른 종목이 그 자리를 대신 채워 "슬롯 수"는 33개로 유지되지만,
  이 두 종목 자체의 틱당 체결빈도가 36~37위권 종목보다 뚜렷이 높은 편이라
  **정성적으로 전체 용량을 20~40%가량 줄이는 효과**로 추정(정확한 수치는 실측
  전까지 신뢰 낮음 — 두 종목의 틱 카운트를 오늘 수집한 tick_al 데이터에서 뽑아
  대조하면 재수집 끝난 뒤 정확히 낼 수 있음)
- 순위 이력 로그(4번)는 위 계산과 별개로 무시할 수준(하루 수 MB 이내)

**최종 추정: 약 30~50MB/일, 월 0.6~1.1GB — 이전 200종목 추정과 비슷한 범위로
수렴했지만 이번엔 실측 기반 하향식 계산이라 신뢰도가 더 높다.** 그래도 "추정"
꼬리표는 유지한다 — 10단호가 실제 압축률은 받아봐야 안다.

## 6-1. 200종목 구독 자체의 커버리지 (별도 질문, 참고용)
"200종목이 전 종목(2,700개) 대비 좁다"는 우려를 로컬 데이터로 확인했다(저장
범위 결정과는 별개 — 소피증권 200종목 **구독** 자체의 적정성 질문).

- 로컬 일봉 1,048종목(전체 시장 2,700여개의 부분집합)으로 2026-08-04~08-28,
  당일 등락률 7~30% 급등 1,274건 발생
- 그중 **57.2%(729건)가 당일 거래대금 200위 밖**이었음
- **주의: 이건 하한치다.** 로컬 데이터가 유동성 높은 1,048종목 위주라 빠진
  나머지 1,650여개(대부분 더 소형·저유동)까지 포함하면 이 비율은 더 높아질
  가능성이 큼(전체 시장 기준으로는 200위 밖 급등 비중이 이보다 낮아지긴
  어렵다 — 빠진 종목들이 200위 안에 들 가능성이 낮으므로)
- 다만 이건 **day-of(당일) 순위** 기준이라 "그날 시작 시점(D-1 기준) 구독
  200종목 안이었는가"와는 다른 질문이다 — 소피증권은 `swap_in()`으로 장중
  동적 편입도 하므로(3번 참고), 실제 놓치는 비율은 이보다 낮을 수 있다.
  하지만 스왑인 조건 자체(`surge_min=3배`, `floor` 규모하한)가 있어 전부
  잡히진 않는다 — 정확한 "실제 놓친 비율"을 내려면 스왑인 로직을 그대로
  시뮬레이션해야 하는데, 지금 요청 범위(호가 저장 설계) 밖이라 여기선 안 함.
  필요하면 별도로 요청해달라.
