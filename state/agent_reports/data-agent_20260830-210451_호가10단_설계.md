## 3. 10단호가 — 새 구독 필요, 타입/스키마 전부 미검증
- 체결(0B)과 호가는 별도 실시간 타입이다. 레거시 키움 OpenAPI+ 관례상 **"0D"=주식호가잔량**
  으로 알려져 있고, 이미 확인된 FID(10,12,13,20,27,28)가 레거시 체계와 일치하는 걸
  보면 0D도 같은 체계를 따를 가능성이 높다 — **하지만 이건 추정이지 이 코드베이스나
  이 세션에서 실측한 사실이 아니다.** 외부 문서 열람 수단이 없어(공식 문서 SPA라
  기존에도 못 긁었음, 이번 세션엔 웹 조회 도구 자체가 없음) 확정 못 함.
- FID 스키마도 마찬가지로 추정: 레거시 관례상 매도호가1~10=41~50, 매수호가1~10=51~60,
  매도잔량1~10=61~70, 매수잔량1~10=71~80 범위로 알려져 있으나 **미검증**.
- **REG의 `data`/`type`이 배열이라는 사용자 지적은 코드로 확인됨** — `feed.py:151`,
  `realtime_feed.py:162`가 이미 `"type": ["0B"]` 형태로 배열을 쓰고 있어 프로토콜
  구조상 추가 타입을 넣는 게 막혀 있지 않음. 다만 **같은 REG 메시지에 0B와 새 타입을
  같이 넣을지, 별도 REG로 나눌지는 안전성 문제라 4번에서 따로 판단한다.**

## 4. 안전 설계 (4가지 절대조건 반영)

### (1) 기존 0B 구독 보호 — 별도 REG로 분리
**같은 REG에 넣지 않는다.** REG 응답은 메시지 전체 단위로 승인/거부되므로(현재 코드도
`if msg.get("return_code")==0`으로 REG 하나를 통째로 판정), 두 타입을 한 메시지에
넣었다가 거부되면 0B까지 같이 날아간다. **별도 REG(`grp_no`를 "2"로 분리)로 보내면
그 REG가 거부돼도 0B의 `grp_no:"1"` 구독은 전혀 영향받지 않는다** — 이게 사용자가
말한 "안전한 쪽"이다. 타이밍도 동시接속이 아니라 **0B REG가 승인된 뒤(`registered=True`
확인 후) 일정 지연(예: 10초) 두고 새 REG를 보낸다** — 혹시 새 타입 자체가 서버 쪽에서
전체 연결에 이상을 일으키는 미지의 버그가 있어도, 0B가 이미 안정적으로 붙은 뒤라
피해가 최소화된다.

### (2) 실패 시 자동 후퇴 — 0B 루프에 영향 없는 예외 처리
새 타입 REG의 응답 핸들러를 0B 핸들러와 분리하고, `return_code != 0`이면:
- 로그+알림(텔레그램, `_notify_baseline_locked`류 패턴 재사용) 남기고
- 그 타입만 "비활성"으로 표시, **재연결 루프에 태우지 않는다**(0B 재연결 로직과
  분리 — 새 타입 실패가 `failures` 카운터에 안 섞이게 별도 상태로 관리)
- 프로세스 종료·예외 전파 금지 — try/except로 감싸 0B 처리 코드 경로와 완전히 분리

### (3) 킬스위치 — 설정 하나, 기본값 꺼짐
`config`(또는 `.env`)에 `ENABLE_ORDERBOOK_10=false` 같은 플래그 하나. **기본값은
꺼짐**(사용자 판단과 일치 — 미검증 상태에서 기본 켜짐은 위험). 사용자가 장중에
문제를 느끼면 이 값만 바꾸고 재시작(또는 핫리로드가 있으면 그것)하면 즉시
되돌아간다 — 코드 롤백이 아니라 설정 하나로 끝나야 한다는 요구사항 반영.

## 7. 오늘 밤 vs 내일 — 권고 (결정은 사용자)
- **오늘 밤 켜는 옵션은 사실상 없다** — 장이 닫혀 있어 무엇을 구독해도 검증할
  데이터 자체가 없다. "오늘 vs 내일"이 아니라 **"내일 09:00에 켤지, 하루 더
  미룰지"**가 실제 선택지다.
- 권고: **내일 09:00에 켜되, 위 안전설계(별도REG·자동후퇴·킬스위치·0B우선확인)를
  전제로 한다.** 근거: (a) 안전설계 자체는 지금 코드/테스트로 이미 검증 가능한
  부분이라 시장 개장과 무관하게 미리 굳혀둘 수 있다 — 즉 "미검증"은 FID 스키마
  이야기지 안전장치 이야기가 아니다. (b) 호가는 과거 조회가 없어 하루 늦추면
  그 하루는 영구 손실인데, 안전설계가 실제로 0B를 보호한다면 손실 없이 얻을 수
  있는 하루를 버리는 셈이다. (c) 반대로 안전설계에 자신 없으면 하루 더 미루고
  코드/테스트만 먼저 굳히는 게 맞다 — **이 부분은 안전설계 코드가 실제로 준비된
  뒤에 다시 판단받아야 한다(아직 코드 구현 전이므로 지금은 방향 제안일 뿐).**
