# data-agent 보고 (2026-08-30) — 웨이브 -> 연속 큐로 교체

## 진단 확인
지적하신 그대로였음 — 저장은 종목 단위로 고쳤지만 **작업 배분은 여전히
웨이브 단위**였음(`wave = remaining[idx:idx+concurrency]`, `with
ThreadPoolExecutor` 블록이 4개 다 끝나야 다음 4개 시작). 종목당 페이지수가
714~2036(약 3배 차이)인 상황에서 가장 느린 종목이 나머지 3명을 계속
붙잡아뒀음 — 4배 기대가 2.8배로 준 진짜 이유.

## 손실 재고 후 즉시 교체
교체 시점(08:50) 기준 새 웨이브 시작 5분째, 완료 0건 — 손실 적음(몇 분 수준)
으로 판단해 바로 교체함. 무거운 종목이 깊이 진행된 상태가 아니었음.

## 구현
`ThreadPoolExecutor(max_workers=4)`에 남은 종목 전체를 한 번에 submit,
`as_completed`로 받음 — 워커 하나가 비면 즉시 다음 종목이 들어감(사용자가
제시한 "후자" 방식 그대로). 웨이브/동시성 증감 개념 자체를 없앰.

종목 단위 즉시저장(threading.Lock)은 그대로 유지 — 오히려 연속 큐에서는
완료가 더 불규칙하게 들어오니 이게 더 중요해짐.

## 429 대응 (연속 큐에서도 동작하게)
워커 수를 동적으로 줄이는 방식은 안 씀 — `ThreadPoolExecutor`는 생성 시
워커 수가 고정이고 스레드를 중간에 강제로 죽일 수 없어서 큐 방식에서는
까다로움(사용자가 예상한 그대로). 대신 **전역 쿨다운**으로 처리: 한 워커가
429를 맞으면 공유 `pause_until` 시각을 60초 뒤로 세팅하고, 모든 워커가
다음 요청 직전에 그 시각까지 대기함(진행 중이던 요청은 안 끊음). 워커 수는
4로 고정한 채 다 같이 잠깐 쉬었다 이어감 — 구현이 단순하고, 재현 테스트에서
429가 아예 안 났으니 지금은 이론적 경로임(실전에서 발동하면 로그로 남음).

## 재측정 예정
방금 교체(08:50:26, 14/115 유지, 손실 없음). 완료가 몇 건 쌓이면 순수
초당 처리량으로 실제 배수를 다시 재서 보고하겠음 — 이번엔 웨이브 경계가
없어서 "종목당 평균 소요시간 × 동시성"이 아니라 "구간 내 완료 건수/구간
경과시간"으로 재는 게 더 정확할 것 같음, 그렇게 계산해서 알리겠음.
