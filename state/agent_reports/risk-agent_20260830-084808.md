# risk-agent 완료 보고 — risk_state_lock 정적분석 추가 발견·수정, 부하 정리

**긴급 조치 먼저**: 지적하신 CPU 부하 확인 즉시 두 repro 프로세스(PID 38900, 35024) `taskkill //F`로 종료. `monitor-nasdaq-drop`(PID 31616) 등 다른 상시 프로세스는 영향 없음을 `Get-CimInstance Win32_Process`로 확인. 이후 CPU 부하를 건 재현은 하지 않았음 — 아래는 전부 정적분석 + 부하 없는 결정적 테스트로만 확인.

**정적분석으로 찾은 진짜 결함 (제안하신 방식대로, 부하 없이 코드만 보고 발견)**: `finally: os.remove(lock_path)`가 무조건 그 경로의 파일을 지웠다. 시나리오 — A가 락 쥐고 오래 작업(예: 주문 여러 건 순차 처리) → 120초(구 LOCK_STALE_SECONDS) 넘음 → 대기자 B가 A를 죽은 걸로 오판, stale 회수해 자기 락으로 새로 만듦 → A와 B가 동시에 임계구역 진입(락의 존재 이유 자체가 깨짐) → A가 나중에 작업 끝내고 finally에서 "그 자리 파일"을 무조건 지움 → 사실은 B의 아직 진행 중인 락을 지운 것 → 세 번째 대기자 C가 끼어드는 연쇄. **부하 재현 없이도 코드만 읽고 확정 가능했던 결함.**

**수정 (`risk_manager.py`)**: (1) 락 파일에 소유 토큰(`pid:thread-id:uuid`) 기록, `finally`에서 토큰이 자기 것일 때만 삭제 — "엉뚱한 락을 지우는" 연쇄만 막음(방어적 조치). (2) `LOCK_STALE_SECONDS` 120→600초로 상향 — "살아있는데 stale로 오판당하는" 근본 확률을 낮춤. **한계 명시**: 이건 확률을 낮춘 것이지 PID 생존확인 같은 완전한 해법은 아니다 — 코드 주석에 승격 경로 남김.

**검증(전부 결정적, CPU 부하 불필요)**: 신규 테스트 `test_risk_state_lock_release_does_not_delete_foreign_lock` — 락 보유 중 파일 내용을 직접 남의 토큰으로 바꿔 "훔침 직후" 상태를 흉내내고, 우리 쪽 해제가 그 파일을 지우지 않는지 확인. 기존 PermissionError 테스트(`test_risk_state_lock_retries_on_transient_permission_error`)도 여전히 통과 — 토큰 로직 추가로 안 깨짐.

**숫자**: `test_risk_manager.py` 48 passed(신규 1건 추가). 제 영역 전체(`test_risk_manager/trading_loop/oversold_trading_loop/cli/dashboard_server`) `231 passed`. 전체 스위트 `812 passed / 6 failed`(무관 파일 `test_trading_value_ranking.py`, 다른 세션이 계속 수정 중이라 실행마다 실패 개수 변동).

**남은 위험**: "락 보유자가 600초 넘게 살아서 작업"은 여전히 이론상 가능(주문 폭주 등) — 그때 오판을 원천 차단하려면 PID 생존확인이 필요하다. 지금은 확률을 낮추는 선에서 멈췄다는 게 정직한 한계.
