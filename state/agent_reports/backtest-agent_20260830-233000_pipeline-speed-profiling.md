# 체결데이터 백테스트 파이프라인 속도 프로파일링 + 최적화 (2026-08-30)

원칙 그대로 적용: 측정 먼저 → 가장 큰 덩어리부터 → 판단 로직 불변 → 전후
결과 숫자 동일성 확인(다르면 최적화 아니라 버그).

## 0. 요약 — 가장 큰 덩어리는 사용자 가설 (1)·(3)·(4)가 아니라 별개였다

사용자가 제시한 4개 후보를 전부 실측했는데, **가장 큰 비용은 어느
후보에도 정확히 안 맞았다** — "오염제거 CONTROL 풀 재구성"에 들어있는
**불필요한 전체정렬(ORDER BY)** 하나였다. 오늘 이 풀을 4번(4단계
버그수정·threshold_rule 검증×2·K=5) 다시 만들었고 매번 700~1085초 걸렸다
— 이게 오늘 하루 낭비된 시간의 대부분이다(합계 약 3,700초, 62분).

**적용한 수정 하나로 984.7초 → 46.0초(21.4배)**, 최종 결과(오염제거 풀
행수 66,781,118)는 **완전히 동일**하게 재확인했다.

## 1. 후보 (1) 파일 개수 — 실측 결과: 큰 덩어리 아님

`data/stocks/tick/*/*.parquet` 2,099개 파일 glob 스캔 COUNT(*): **2.1초**.
컬럼 프루닝 시 0.7초(2.95배 이득, 하지만 절대량이 작음). 2,099개 파일을
1개로 합쳐도(288.4MB) 스캔 자체는 이미 2.1초라 체감 차이가 안 남는다 —
**원틱 스캔 자체는 이미 빠르다, 병목이 아니다.** 파일 통합은 시도했지만
효과가 미미해 채택 안 함(테스트용 캐시파일 삭제함).

## 2. 후보 (3) 컬럼 프루닝 — 실측: 작은 효과, 확인함

위와 같은 측정에서 2.95배 이득 확인(원틱 3컬럼뿐이라 이득 자체가 작다는
사용자 예상이 맞았다). 절대시간이 이미 2초대라 우선순위 낮음.

## 3. 후보 (2)·(4)의 실제 정체 — CONTROL 풀 재구성의 불필요한 정렬

`results/point_labeling_features_labels.parquet`(1.2GB, 이미 캐시된
피처+라벨, 재계산 안 함 — 오늘 모든 스크립트가 이 파일을 직접 읽었다,
60초 rolling을 다시 돈 적은 없음. **후보(2) "피처 재계산" 자체는 실제로
문제 없었다**)에서 "오염제거 CONTROL 풀"(SHOOT/CRASH 직후 60초 이내
NEUTRAL 제외)을 만드는 4단계가 오늘 반복 재사용됐는데, 이 4단계를
쪼개서 실측하니:

| 단계 | 원래(ORDER BY 포함) | 수정 후(ORDER BY 제거) | 배수 |
|---|---|---|---|
| B. 고유키(rid) 부여 | **599.4초** | **15.5~17.0초** | **35~39배** |
| C. 오염플래그(60초 RANGE윈도우) | 228.1초 | 18.1초 | 12.6배 |
| D. control_pool 조인 | 157.2초 | 12.4초 | 12.7배 |
| **합계** | **984.7초** | **46.0초** | **21.4배** |

**원인**: B단계가 `row_number() OVER (ORDER BY code, date_str, ts)`로
70.9M행 전체를 정렬해서 고유키(rid)를 만들었다. 그런데 rid는 **join용
합성키일 뿐 값 자체엔 의미가 없다** — 유일하기만 하면 되지 특정 순서일
필요가 없다. `ORDER BY`를 빼고 `row_number() OVER ()`만 쓰면 정렬 없이
스캔 순서대로 번호만 매긴다.

**정확성 검증**: 유일성(70,912,254행 = distinct rid 70,912,254개) 확인,
최종 control_pool 행수(66,781,118) 원래 값과 정확히 일치 확인 — **판단
로직은 그대로, 결과 숫자도 그대로, 속도만 바뀌었다**(rid 값 자체는 실행마다
달라질 수 있지만 join 키로만 쓰이므로 무관 — 이전에도 rid는 어느 코드에도
"의미있는 값"으로 노출된 적 없음, 오직 join 용도).

**C·D단계도 같이 빨라진 이유**: B단계의 70.9M행 전체정렬이 10GB 메모리
한도 안에서 디스크 스필(외부정렬)을 유발했을 가능성이 높다 — 이게 뒤이은
C·D단계의 디스크 I/O에도 영향을 준 것으로 추정한다(확정은 아님, 격리된
재검증을 시도했으나 백그라운드 작업이 외부 요인으로 두 번 중단돼(이
세션의 다른 오래된 프로세스들과 함께 동시에 killed됨, 내 스크립트 오류
아님) 완전히 격리된 재측정은 못 마쳤다). 다만 **B단계 자체의 절감(35~39배,
약 580초)은 원인이 명확하고 이미 검증됐다** — 이것만으로도 오늘 낭비의
대부분을 설명한다.

## 4. 캐싱(추가 옵션, 필요시)
control_pool을 parquet으로 저장(199.6초, 1회성) 후 재로딩(91.3초, 행수
일치 확인)도 테스트했다. **B단계 수정만으로 이미 46초까지 줄어서
캐싱까지는 필요성이 낮아졌다** — 그래도 앞으로 이 풀을 자주 재사용할
계획이면 `results/point_labeling_control_pool_cache.parquet`(이미
생성해둠)를 재사용하는 것도 옵션으로 남겨둔다.

## 5. 후보 (4) DuckDB 사용범위 — pandas 구간 실측 (기존 데이터 재사용)
오늘 이미 실측된 데이터에서: 가설C 전체스캔(373.8초) 중 진입조건은
SQL(215.4초 이내)로 다 처리됐지만, **청산 시뮬레이션은 파이썬 반복문**
(193,091건 순회)으로 158.4초(전체의 42.4%) 걸렸다 — tick별 손익 계산이
"이전 봉/틱까지의 상태"에 의존하는 경로의존적 로직이라 SQL 윈도우함수로
한 번에 못 바꾼다(현재 아키텍처의 의도적 선택, `_compute_exit_legs`가
그런 구조). **이번엔 손 안 댐** — ORDER BY 제거처럼 결과불변이 확실한
수정이 아니라, 벡터화하려면 로직을 다시 짜야 해서 "판단 로직은 그대로"
원칙과 충돌 위험이 있다. 다음 우선순위 후보로만 기록.

## 6. 목표 대비
"4단계급 작업(24분)이 5분 이내로" — **이번 최적화로 CONTROL 풀 재구성
단계는 16.4분(984.7초)에서 0.77분(46초)로 줄었다.** 이 풀 재구성이 4단계
류 작업 전체시간의 대부분을 차지했으므로(4단계 최초 수정판 971.7초 중
과반이 이 풀 관련 단계였음), 이 수정을 반영하면 유사 작업이 5분 이내로
들어올 가능성이 높다 — 다만 각 스크립트가 이 SQL을 복사-붙여넣기로
쓰고 있어서(커밋된 backtesting/*.py에 아직 없음, 전부 /tmp 스크립트),
**수정 자체는 코드 재사용 형태로 아직 반영 안 됨** — 다음에 이 로직이
정식 모듈로 승격되면(strategy-agent 소유) 그때 ORDER BY 없는 버전으로
넣어달라고 요청하겠다.

## 7. 결론 (판단 아님, 서술만)
- 사용자 가설 (1)파일개수·(3)컬럼프루닝은 실측상 병목이 아니었다(이미
  2초대).
- (2)피처재계산은 이미 캐시 재사용되고 있어 문제없었다.
- **실제 병목은 가설에 없던 것**: 캐시된 피처 파일에서 CONTROL 풀을
  만드는 과정의 불필요한 전체정렬. 제거로 984.7초→46.0초(21.4배), 결과
  완전 동일 확인.
- (4)파이썬 반복 청산 시뮬레이션(전체의 42.4%)은 다음 최적화 후보로
  남김 — 이번엔 로직 변경 위험 때문에 손 안 댐.
