# risk-agent 완료 보고 — risk_state_lock 간헐 실패 원인 규명·수정

**판정: 둘 다였다.** 처음엔 테스트 문제(Case 1)만 있는 줄 알았는데, 부하 재현 중 진짜 코드 결함(Case 2)도 하나 더 나왔다.

**재현 방법**: 임시 스크립트로 8개 CPU-hog 스레드(GIL 경합 유발)를 띄운 채 락 테스트 로직을 반복 실행. 30초 join 기준 다수 재현 성공.

**Case 1 — 테스트 결함 (확정, 락은 무죄)**: 실패 시 상태 파일을 직접 열어보니 포지션 코드가 `A000~A015, B000~B009`처럼 항상 "0번부터 연속, 중간 구멍 없음"이었다 — 유실이면 중간이 듬성듬성 빠져야 하는데 그게 아니라 "거기까지만 진행됨"이었다. `alive=[True, True]`도 매번 확인 — `join(timeout=30)`이 만료됐을 뿐 워커가 그냥 아직 도는 중이었다. **수정**: `test_risk_manager.py:268` — join 타임아웃을 300초(교착 감지용 안전장치로만)로 늘리고, join 직후 `assert not t.is_alive()`로 "안 끝남"과 "유실"을 명시적으로 분리.

**Case 2 — 진짜 코드 결함 (발견·수정함)**: 부하 재현 중 `PermissionError: [Errno 13] Permission denied: '...risk_state.json.lock'`가 워커를 그대로 죽였다(`risk_manager.py:128`, 당시 `except FileExistsError:`만 있었음). Windows(NTFS)는 락 파일이 막 삭제된 직후 같은 이름을 다시 만들려 하면 FileExistsError 대신 PermissionError를 던지는 경우가 있음 — 재시도 루프가 이 예외를 안 잡아 죽었다. 실거래라면 `run_trading_loop` 전체가 예외로 죽는 것과 동일. **수정**: `risk_manager.py:141` `except FileExistsError:` → `except (FileExistsError, PermissionError):`.

**검증**: 신규 결정적 단위테스트 `test_risk_manager.py:324`(`os.open` 모킹으로 PermissionError 1회 강제 발생 후 재시도 성공 확인, 부하 불필요) 추가·통과. 기존 락 테스트 5회 연속 재실행(다른 백그라운드 작업들이 실제로 CPU를 먹고 있는 상태에서) 전부 통과. 제 영역 테스트 `230 passed`(test_risk_manager/trading_loop/oversold_trading_loop/cli/dashboard_server).

**한계**: 대규모(8×8) 부하 재현 스트레스 테스트는 시간이 오래 걸려 이 보고 시점까지 끝까지 지켜보지 못함(백그라운드에서 계속 실행 중이었을 수 있음) — 다만 결정적 단위테스트로 같은 코드 경로를 이미 검증했으므로 완료를 기다릴 필요는 없다고 판단. 재현용 임시 스크립트(`repro_lock_race.py`)는 삭제함(커밋 대상 아니었음).

**남은 위험**: 전체 스위트 `809 passed / 8 failed` — 실패 8건은 `test_trading_value_ranking.py`/`test_universe.py`로 제 작업과 무관, 다른 세션이 지금도 그 파일들을 동시 수정 중이라 실패 개수가 실행마다 바뀜(4건→8건).
