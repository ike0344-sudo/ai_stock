## DuckDB 후보 판단 — "느림"과 "엔진 의존"을 나눠서 봐야 한다

느린 스크립트라고 다 SQL 후보는 아니다. 코드를 직접 열어 두 갈래로 갈렸다:

**엔진 의존(NOT SQL 후보)**: chgtop_swap.py / clean20_theme_edge.py / **rank_timeline.py**
— 셋 다 `Aggregator`+`score_themes`(실시간 엔진의 상태 유지 스코어링 로직, 구독
교체·테마 가중치·핀고정/제외 규칙 등)를 분단위로 재생한다. **rank_timeline.py는
이름 때문에 "윈도우 함수 형태"로 짐작했지만(과제 지시에도 그렇게 적혀 있었다),
실제로는 그 반대다** — 겉보기엔 "순위를 시간순으로 훑는" 루프지만, 매 분마다
호출하는 내용물이 라이브 엔진의 전체 상태기계(구독 교체·핀/제외·테마 카운트)라
lead가 이미 실시간 엔진 자체를 SQL 대상이 아니라고 판단한 것과 같은 이유로 이것도
후보가 아니다. 이름만 보고 판단하면 틀린다는 걸 이번에 직접 코드를 열어 확인했다.

**엔진 미사용(SQL/DuckDB 후보)**: **chgtop_hold.py(296.86s, 최느림)**,
rising_threshold.py(257.05s), flow_distribution.py(128.20s), rising_test.py(99.13s),
entry20.py(78s) — 전부 코드를 열어 확인: 날짜×종목(×테마) 중첩 파이썬 for문으로
합계/비율/순위 같은 단순 집계만 한다(순차 상태의존 로직 없음 — trailing stop 같은
first-passage 문제가 아니라 스냅샷 집계). 구조적으로
`intraday_top_n_return_rank1_by_minute`/`detect_entries`와 같은 성격이라 이미 이
세션에서 검증한 포팅 패턴을 그대로 적용할 수 있어 보인다. 우선순위는 느린 순서
(chgtop_hold → rising_threshold → flow_distribution → rising_test → entry20)로 두면
될 것 같다. **단, 실제 포팅은 하지 않았다** — 측정과 판단만 이번 지시 범위.

## 항목 2: 실시간 엔진(app/engine/runner·scoring·aggregator) — lead 판단 확인

**lead 판단이 맞다.** app/main.py의 `start_index_poller`(실제 운영 중인 폴링 루프,
`sophie_bot.py`와는 다른 프로세스 — sophie_bot은 텔레그램 조회봇일 뿐 이 폴러가
아니다)와 완전히 같은 순서로 실제 라이브 API(읽기 전용, 주문 없음, 시세 조회만)를
두 번 독립 실행해 측정:

| 단계 | 1차 | 2차 |
|---|---|---|
| index_quote(001) | 0.176s | 0.214s |
| index_quote(101) | 0.990s | 0.950s |
| index_ma_spread(001) | 1.114s | 1.127s |
| trading_value_top(pages=3, 233종목 반환) | 3.262s | 3.246s |
| **API 합계** | **5.542s** | **5.536s** |
| 로컬 계산(seed_today/swap_in 상당, 233행 순수 반복) | 0.0001s | 0.0001s |
| **API 대기 비중** | **100.0%** | **100.0%** |

두 번 측정이 거의 완전히 일치(재현성 확인). 로컬 계산은 반올림하면 0%로 잡힐
정도로 미미하다 — API 응답 대기(`_MIN_INTERVAL=1.1초` 자체 쓰로틀 + 실제 네트워크
왕복)가 사이클 시간을 전부 차지한다. 폴링 간격(INDEX_POLL_SEC=30초, 개장 구간만
20초)에 여유가 있어 지연으로 사이클을 놓치는 문제도 없다. **DuckDB/SQL로 옮길
계산 자체가 없다 — 병목이 계산이 아니라 API라는 lead 판단이 실측으로도 맞다.
건드리지 않는다.**
