## 정정 — 사용자 가설 중 하나가 틀렸음(중요)
"open/high/low가 cur_prc와 100% 같다"는 맞았음(175개 파일 전수 확인, 위반 0).
하지만 **"pred_pre_sig가 파일 내 상수"라는 가정은 틀렸음** — 175개 중 132개
(75%)에서 하루 중 값이 2/3/5(상승/보합/하락)로 바뀜(전일종가를 여러 번
넘나드는 게 정상이라 당연함). "cur_prc-pred_pre가 상수"도 틀렸음(부호 없이
뺐기 때문). 대신 **부호를 살려서**(2=+,3=0,5=-) 뺀 값은 175개 전부에서
파일 내 상수였고, 그 값이 로컬 일봉의 직전 거래일 종가와 정확히 일치함
(009150 2026-08-03에서 실측 확인: 1,142,000원 = 1,142,000원). 그래서
pred_pre/pred_pre_sig 둘 다 파일당 상수 하나(ref_price)로 대체 가능함 —
당초 예상(5개 버림)보다 나은 결과(open/high/low 3개 + pred_pre/sig 2개 =
5개 그대로 버림, 다만 방법이 달랐음).

## (3) 형식 — Parquet 압도적 우세, 실측 근거
175개 파일(523.86MB) 기준:
| 형식 | 크기 | 원본 대비 |
|---|---|---|
| 원본(8컬럼 CSV) | 523.86 MB | 100% |
| 압축 CSV(4컬럼, ref_price 컬럼 포함) | 237.59 MB | 45.4% |
| 압축 Parquet(3컬럼 + ref_price는 파일메타) | 35.80 MB | **6.8%** |

Parquet이 압축CSV보다도 6.6배 작음 — 컬럼 지향 압축이 반복값(같은 cur_prc가
여러 틱에 걸침)·정렬된 시각값에 특히 잘 먹힘. pyarrow는 이미 설치돼 있어
새 의존성 없음. pandas 호환성: `pd.read_parquet()`으로 그대로 읽힘, 백테스트
쪽에서 추가 설정 불필요.

## (4) 절대조건 — 전수 검증 + round-trip 확인 후 삭제
- 전수 검증(175개 파일): open=high=low=cur_prc 위반 0건, 부호적용 기준가
  상수성 위반 0건 — 지금까지 압축 못 할 파일 없음(있었다면 원본 CSV로 남기게
  코드에 이미 넣어둠, `tick_compact_daemon.py`가 파일 단위로 판단).
  - `pred_pre`가 항상 양수(부호 없음)인지도 확인함 — `pred_pre_sig`가 방향을
    따로 담당하는 구조라는 걸 확인함.
- round-trip: 175개 전부 압축->복원 후 원본 8컬럼과 완전 일치(불일치 0건).
  실제 운영 데몬도 **디스크에 쓴 parquet을 다시 읽어** 복원값을 원본과
  비교한 뒤에만 원본 CSV를 지움(메모리상 비교가 아니라 디스크 왕복까지
  확인) — 오늘 ka10079 사고("성공 처리됐는데 실제로는 아님")를 반복하지
  않기 위함.
- 지금까지 9종목·171개 파일 압축, 스킵 0건, round-trip 불일치 0건.
