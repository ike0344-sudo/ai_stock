# intraday_new_high_filter DuckDB 포팅 실험 결과 (2026-08-30)

지시대로 조건 하나(가장 단순한 cummax 조건)만 먼저 포팅해봤다. detect_final_entries/
scan_all_trades에는 아직 연결하지 않았다 — 이 함수 단독으로만 존재한다.

## 한 일
- `backtesting/entry_filters.py`에 `intraday_new_high_filter_batch_duckdb(data_dir)`
  추가. 기존 `intraday_new_high_filter(minute_candles)`(종목 1개씩 호출하는 pandas
  버전)는 그대로 유지 — 코드/시그니처 둘 다 안 건드림.
- SQL: `high >= MAX(high) OVER (PARTITION BY code, day ORDER BY ts ROWS UNBOUNDED
  PRECEDING)` — pandas의 "날짜별로 그룹핑 후 cummax" 로직과 동일한 걸 종목 전체에
  대해 한 번에 계산.
- 반환 형태는 `{code: pd.Series[bool]}` (기존 함수가 종목 1개당 내는 Series와 값이
  같아야 함).

## 검증
- `tests/backtesting/test_entry_filters.py`에 `test_intraday_new_high_filter_batch_duckdb_matches_pandas_version`
  추가 - 기존 pandas 단위테스트와 같은 시나리오(신고가/비신고가 섞임 + 날짜경계
  넘어갈 때 리셋되는지)를 2종목으로 재구성해 두 구현이 완전히 같은 Series를
  내는지 확인. **18/18 통과**(기존 16개 포함).
- 실측: 로컬 전체 1045종목 대상으로 pandas 버전(종목별 반복 호출)과 duckdb 배치
  버전을 나란히 돌려 **종목 1045개 전부 완전 일치(불일치 0)** 확인.

## 속도
| 구현 | 소요시간 |
|---|---|
| pandas (종목별 반복, CSV 읽기 포함) | 81.63초 |
| DuckDB 배치(전체 종목 한 번, CSV 읽기 포함) | 24.83초 |
| 배수 | **3.3배** |

⚠️ 이 3.3배는 "이 조건 계산 하나만 처음부터 끝까지(CSV 읽기 포함) 독립적으로 다시
돌렸을 때"의 배수다. `scan_all_trades` 안에서는 같은 minute CSV를 다른 목적
(simulate_trade_path, 다른 조건들)으로도 어차피 한 번 읽어야 하므로, 이 조건만
쏙 빼서 batch로 바꾼다고 CSV 읽기 비용까지 통째로 절약되는 건 아니다 — 실제로
`detect_final_entries` 안에 끼워 넣었을 때의 순증분 이득은 이 3.3배보다 작을
가능성이 크다(cummax 자체의 순수 계산 비용만큼만 줄어듦). 정확한 순증분은
실제로 연결해봐야 안다 - 지금은 조건 자체의 포팅 가능성과 정확성만 검증한 단계.
