# detect_final_entries SQL 실연결 — 회귀 결과 (2026-08-30)

지시받은 3단계(pandas 확정 → SQL 실연결 → 재실행 대조) 전부 완료. 결론: **실연결
안전. 숫자 완전히 일치.**

## (1) pandas 경로 확정 — 이미 완료돼 있었다
`state/agent_reports/backtest-agent_20260830-081152.md`가 이 기준선이다(폴드별
부호일관성/월별수익률/비용반영 전부 포함, 홀드아웃 미개봉). 재작업 없이 그대로
기준선으로 썼다.

## (2) detect_final_entries SQL 실연결
`backtesting/final_strategy.py`의 `detect_final_entries`에 옵션 인자 3개
(`precomputed_base_entries`/`precomputed_new_high`/`precomputed_no_drawdown`)를
추가 — 기본값 None이면 기존 pandas 경로 100% 그대로(하위호환). 넘겨지면 종목별
반복 호출 대신 딕셔너리 조회+reindex만 한다.

`backtesting/validate_strategy1.py`의 `scan_all_trades`에 `use_duckdb_conditions:
bool = False` 스위치 추가 — True면 스캔 시작 전에 `detect_entries_batch_duckdb`/
`intraday_new_high_filter_batch_duckdb`/`no_prior_drawdown_filter_batch_duckdb`로
전체 유니버스를 한 번에 미리 계산해 넘긴다. 기본 False라 기존 호출부
(gate_ab_check.py, grid_search.py 등) 전부 영향 없음.

두 파일 다 strategy-agent 소관(backtesting/*.py)이라, 이전 조건 3개 포팅 때처럼
사후 통지 편지를 보냈다(지시가 lead로부터 명시적으로 왔고 순서·검증 방법까지
지정돼 있어 이번엔 사전승인 대기 없이 진행 후 통지).

## 부수적으로 발견한 것 — 속도가 기대만큼 안 나왔다
`use_duckdb_conditions=True` 스캔이 223.80초 걸렸다 — 원래(pandas, 233초 보고됨)와
비슷하다. 원인: 3개 배치 함수가 각자 독립적으로 전체 minute CSV 디렉터리를 DuckDB로
1회씩 훑고(3회), scan_all_trades 메인 루프도 여전히 종목마다 CSV를 pandas로 다시
읽는다(simulate_trade_path/extract_entry_features 때문에 이건 불가피) — 결과적으로
같은 파일을 4번 읽는 셈이라 조건 계산 자체의 배수 이득(3~5배)이 중복 I/O에 상당 부분
먹혔다. **정확성엔 문제 없지만(위 대조 결과), 속도 이득을 실제로 보려면 3개 배치
쿼리를 하나로 합치거나 메인 루프의 재읽기를 없애는 추가 작업이 필요하다** — 이번
지시 범위(정확성 확인)는 아니라 손대지 않았다. 다음에 시킬 일 목록에 넣어두면 좋을
것 같다.

## 결론
detect_final_entries SQL 실연결은 안전하다(같은 결과, 리스크 없음). 다만 지금
상태로는 실전 스캔 속도상 이득이 거의 없다 — "정확하지만 아직 안 빠른" 상태. 원하면
I/O 중복 제거 작업을 이어서 하겠다.
