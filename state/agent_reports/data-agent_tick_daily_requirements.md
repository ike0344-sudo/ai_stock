# 체결(ka10079) 상시 자동 수집 — 필요 시 참고용 요구사항 문서 (등록 안 함)

**주의: 이 문서는 설계 참고용이다. 사용자 지시로 지금은 등록하지 않는다 —
"명확한 필요 사례"가 확인된 뒤 다시 논의한다(2026-08-30).** 아래는 그때 바로
쓸 수 있도록 이번 8/03~8/28 일회성 수집(117종목, 19일치)에서 실측한 값 기준.

## 1. 소요 시간
- 이번 일회성 백필(19일×117종목)은 동시성4로 약 4~5시간 소요(재시작 포함 실측)
- **상시화 시 매일 필요한 작업은 "그날 하루치"만**이라 훨씬 짧다 — 종목당
  페이지수가 19일치로 455~2266이었으니 하루 평균 24~120페이지 추정. 종목수를
  top35 당일 기준(약 35~40종목, 지금의 117은 19일 누적 합집합이라 훨씬 큼)으로
  좁히면, 동시성4 기준 총 소요는 대략 10~30분대로 추정(실측 아님 — 상시화
  시작하면 첫 며칠 실측해서 이 문서 갱신 필요)

## 2. 용량
- 이번 117종목×19일 결과물: 386MB(parquet 압축 후, 원본 CSV 대비 약 6.8%)
- 하루치·top35 규모(35~40종목)로 추정하면 대략 15~20MB/일 — 1년 약 250거래일
  기준 4~5GB/년 수준(대략치, 실측 아님)

## 3. 실행 시각
- 장 마감(15:30) + 여유 후 — 기존 `top35_job.py`가 15:40에 도는 것과 맞춰
  15:40 이후가 자연스러움(같은 계정 API를 다른 봇들과 나눠 쓰므로 완전히 겹치지
  않게 시차를 두는 게 안전 — 이번 수집 중 다른 실거래 봇에 영향 없음은 확인됐지만
  그건 장중이 아니라 이번처럼 24시간 상시 도는 상황에서였다는 점 유의)

## 4. 장중 정지
- 이미 구현돼 있음(`tick_collect_803_828.py:pause_if_market_hours`) — 09:00~15:30
  사이엔 페이지 요청 직전마다 확인해 자동 정지, 15:35 이후 재개. 상시화해도
  이 로직 그대로 재사용 가능

## 5. 백필 방식
- 최초 1회는 원하는 기간만큼 지금처럼 대량 백필 필요(20거래일 조회창이 있어
  묵혀두면 과거분이 밀려남 — 이번 사고의 원인과 동일)
- 이후는 **증분만**: 어제까지 받은 마지막 날짜 다음날부터 오늘까지만 요청
  (지금 코드는 "START_DATE까지 페이지네이션" 방식이라 상시화하려면 "어제 이후만"
  으로 종료조건을 바꿔야 함 — 지금 코드 그대로 매일 돌리면 매번 20일 전체를
  다시 받아 비효율적)

## 6-1. 경계일 절단 함정 (2026-08-30 실제로 겪음, 반드시 반영)
목표 시작일(START_DATE)에 "처음 닿는 순간" 멈추면 그 날짜는 **일부만** 들어온다
— ka10079는 최신부터 과거로 페이지네이션하는데, 종료조건을 `min_date_seen <=
START_DATE`로 짰더니 시작일의 늦은 시각(장마감 근처) 한두 페이지만 저장되고
이른 시각(장시작 쪽)은 통째로 빠졌다(실측: 109종목 전부 8/03이 09:00이 아니라
11:01~15:19 사이 어딘가부터만 남음 — 유동성 높을수록 페이지 하나가 짧은 시간만
담아 더 심하게 잘림). **반드시 목표 시작일보다 하루(또는 그 이상, 연휴 등 고려)
더 이전까지 페이지네이션한 뒤, 저장 시점에만 목표 범위로 필터링해야
그날 전체가 온전하다** — 종료조건은 `min_date_seen < START_DATE`(엄격 부등호)로
잡을 것. 이 문서 작성 시점 기준 코드는 이미 수정 완료(`tick_collect_803_828.py`).
상시화(매일 증분) 버전을 새로 짤 때도 "어제까지 받은 마지막 날짜"가 아니라
"어제까지 받은 마지막 날짜의 하루 전"부터 페이지네이션을 시작해 첫날 경계도
같은 함정에 안 걸리게 할 것.

## 6. 감시 방법
- **이번에 실제로 겪은 문제**: 수집기 프로세스가 원인불명으로 조용히 죽어
  23분+ 방치된 적 있음(data-agent_20260830-111600.md) — 상시화하려면 반드시
  워치독 필요, 최소한:
  - 로그 최종 갱신 시각이 예상 실행시간(15:40~조금 후)을 넘도록 오래됐는데
    프로세스가 없으면 알림/재시작(monitoring-agent의 agent-poke.ps1 방식 참고)
  - progress.json류 상태파일로 "오늘자 수집 완료 여부"를 다른 에이전트/대시보드가
    바로 확인할 수 있게 노출
- partial(불완전) 자동 처리 주의: 이번에 "partial을 자동으로 done 처리"하는
  경로가 문제였다(000880 사고, 이후 코드 수정함) — 상시화해도 partial은 자동
  승인하지 말고 항상 재시도 대상으로 남기거나 사람이 검토하게 할 것
