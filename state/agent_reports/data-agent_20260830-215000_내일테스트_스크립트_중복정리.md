# data-agent 20260830-215000 — 내일 웹소켓 테스트, monitoring-agent 스크립트로 단일화 권고

## 중복 발견
monitoring-agent가 나와 독립적으로 같은 목적의 스크립트를 이미 만들어뒀다
(`backtesting/websocket_collision_probe.py` + `docs/WEBSOCKET_SESSION_TEST_20260831.md`,
`monitoring-agent_20260830-2140` 보고). 내가 만든 `ws_dual_connection_probe.py`
+ `data-agent_20260830-211500_내일0800테스트절차.md`와 목적이 완전히 같다 — 둘 다
"같은 appkey로 두 번째 0B 연결을 열어 소피증권과 공존하는지 본다"는 동일 테스트.

## 비교 후 판단: monitoring-agent 쪽을 채택한다
직접 코드 대조한 결과, monitoring-agent 쪽이 더 안전하다 — **정직하게 인정한다**:
- **하드컷 방식이 다르다.** 내 스크립트는 `--minutes`(상대시간, 08:20에 시작한다는
  전제 하에 20분 후 종료)를 썼는데, monitoring-agent는 `--hard-stop-hhmm`(절대
  시각, 기본 "0850")을 썼다. **내 방식은 시작이 늦어지면 08:50을 넘길 수 있다**
  (예: 08:35에 실수로 시작하면 08:55까지 돎) — 이건 사용자가 가장 걱정한 "09:00에
  소피증권만 남아있어야 한다"는 요구를 상대시간으로는 확실히 보장 못 한다.
  monitoring-agent 방식은 시작 시각과 무관하게 절대 08:50을 못 넘긴다.
- monitoring-agent는 생존 확인용 하트비트 파일(`heartbeat.json`)까지 만들어
  외부에서 프로세스가 죽었는지도 확인 가능하게 했다 — 내 것엔 없음.
- monitoring-agent는 관찰 오염 방지를 위해 재연결 로직을 의도적으로 뺐다고
  명시했다 — 나도 재연결을 안 넣긴 했으나 그 이유를 문서화하지 않았다.
- 관찰 전용 도구(`sophie_prelaunch_watch.py`, 소피증권 로그·app.log·`/api/market`
  세 곳 동시 관찰)도 이미 만들어져 있고 **실제 라이브로 10초 스모크테스트까지
  했다** — 내 쪽엔 이런 관찰 도구가 없었다.
- 테스트 23개 작성·통과까지 돼 있다 — 내 스크립트는 단위테스트가 없다.

실행하지 않는다 — 세 번째 연결까지 겹치면 테스트 자체가 오염된다.
