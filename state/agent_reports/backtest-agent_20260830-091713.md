# no_prior_drawdown_filter DuckDB 포팅 결과 (2026-08-30)

intraday_new_high_filter와 같은 패턴으로 두 번째 조건 포팅.

## 한 일
- `backtesting/entry_filters.py`에 `no_prior_drawdown_filter_batch_duckdb(data_dir,
  drawdown_threshold)` 추가. 기존 `no_prior_drawdown_filter(minute_candles,
  drawdown_threshold)`는 그대로 유지.
- SQL: 고점(MAX(high) OVER ROWS UNBOUNDED PRECEDING) → 하락폭 판정(CASE) →
  판정의 cummax(MAX(...) OVER ROWS UNBOUNDED PRECEDING) — 윈도우함수 두 겹으로
  "한 번 발동하면 그날 계속 False" sticky 로직을 그대로 표현.
- `detect_final_entries`에는 아직 연결 안 함(조건 단위 검증만).

## 검증
- `tests/backtesting/test_entry_filters.py`에 동일성 테스트 추가(발동전/발동후sticky/
  날짜경계리셋 3시나리오, 종목 2개로 재구성) — **19/19 통과**.
- 실측: 로컬 전체 1045종목 pandas vs duckdb 배치, **전 종목 완전 일치(불일치 0)**.

## 속도
| 구현 | 소요시간 |
|---|---|
| pandas(종목별 반복, CSV 읽기 포함) | 82.54초 |

intraday_new_high_filter(3.3배)와 거의 같은 배수 — 두 조건 다 CSV I/O 비중이 커서
순수 계산 자체의 배수는 이보다 크지만(cummax/윈도우함수 자체는 훨씬 빠름) 조건
단독 벤치마크로는 I/O가 대부분을 가린다는 점은 지난 보고와 동일한 caveat.
